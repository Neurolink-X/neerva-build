# Bounded recovery and security
- Public read pages retry their React boundary once per path per tab per ten minutes, only while online and visible. No root-layout auto reload, no storage clearing and no automatic payment/order resubmission.
- The authenticated operations helper rejects non-API and external destinations and refuses redirects. GET only: one transient retry for 502/503/504 or eligible network/timeout failure, with jitter and same user/token confirmation. No retry after explicit 429/403 or mutations; existing same-account 401 refresh remains bounded. Other callers are not automatically covered.
- Existing role/RLS, rate limiting, release contract, dependency audits and incident monitor remain intact. Browser recovery is not proof that a server incident is resolved. No automatic source edits, privilege changes, deployment retries or security bypass.
- CI local-browser performance target LCP 2.5s, CLS .1, TTFB .8s; severe ceilings 8s/.25/4s block smoke. Missing samples are reported, not treated as measured success. Local timings are not actual field measurements.
- Security header checks run in browser CI; service worker script revalidates rather than serving stale code. CSP is currently restrictive for framing/forms/objects but not a full script-src policy; test a report-only nonce policy before enforcing it.
- Remaining: production field telemetry/alerting, privileged account MFA enforcement, CSP rollout, penetration tests, independent backups/restore drills and reviewed rollback procedures. No promise of uninterrupted operation or immunity from attackers.

- A weekly GitHub Actions read-only production watch (Monday 03:23 UTC, 08:53 IST) and manual dispatch use fixed approved origins, bounded timeouts and one retry. Catalog/config degradation fails the job instead of reporting healthy. No install or production deployment; consumes a small amount of GitHub runner allowance. GitHub Actions notifications depend on account preferences. It does not provide continuous uptime monitoring or automated rollback.

- Admin System Health reads the protected incident API while the page is visible, every 15 seconds after a successful fetch, with 30/60/120-second backoff for failures. Reconnect/focus resumes checks. Browser incidents are dispatched immediately on a best-effort basis through the existing signed-in incident RPC; they do not await the weekly workflow. No anonymous telemetry endpoint, new database permissions, or production database migration. The live database inspection found incident RLS enabled with administrator SELECT policy, but the table is not in the Realtime publication; bounded polling is used instead of widening access. The panel cannot report during a total hosting/database outage and does not send background push notifications. A failed refresh hides incident data and clearly marks monitoring unavailable. Review notes are not reset during routine successful refreshes.

- Shared operations requests now classify HTTP and transport failures without exposing raw 5xx payloads, keep safe transaction verification instructions and display validated references. Existing validation/conflict details remain available. Hindi recovery text on page boundaries. Admin incident cards show first/last observed time, available trace ID and conditional troubleshooting steps. Optional admin diagnostics validate real public catalog and studio configuration responses. Those two routes mark fallback responses degraded, not healthy; signed-in browser monitor records the existing allowlisted incident signal. Anonymous errors and failures during a full database outage are not guaranteed to reach the admin table; inspect hosting logs. No database schema or permission changes. Browser telemetry is best-effort and reports observed failures, not verified causes.
